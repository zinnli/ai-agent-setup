# review-diff

변경된 diff를 리뷰하는 절차다. 스타일 지적보다 동작·설계 문제를 우선한다.

## 절차

### 1. 변경 범위 파악
- `git diff` / `git diff --staged`로 변경 내용을 확인한다.
- 변경의 의도(무엇을 위한 diff인지)를 먼저 이해한다.
- 변경 파일과 영향 범위를 훑는다.

### 2. 우선순위대로 리뷰
아래 순서로 확인한다. 위쪽이 더 중요하다.
1. **정확성** — 로직 오류, 경계 조건, 예외·에러 처리 누락, 비동기 처리
2. **설계** — 책임 분리, 불필요한 복잡도, 중복, 재사용 가능한 기존 코드 무시
3. **프론트엔드** — 상태 관리 위치, 훅 규칙, 의존성 배열, 렌더링 key, 접근성
4. **타입** — `any`/무분별한 단언, 좁혀지지 않은 타입, 공개 API 타입 누락
5. **테스트** — 변경에 대한 테스트 유무, 사용자 관점 검증 여부
6. **컨벤션** — 네이밍·포맷·프로젝트 패턴 일치

### 3. 리스크 확인
- 시크릿·민감 정보가 코드나 로그에 노출되지 않는지 확인한다.
- 되돌리기 어려운 변경이나 기존 동작 회귀 가능성을 점검한다.

### 4. 정리
- 발견 사항을 심각도(치명/권장/사소)로 나눠 정리한다.
- 각 항목은 `파일경로:줄번호`와 함께, 문제와 개선 방향을 제시한다.
- 확신과 추측을 구분해 표현한다.

## 완료 기준
- 우선순위 항목을 모두 훑었다.
- 발견 사항이 심각도별로 위치와 함께 정리되어 있다.
- `resources/review-checklist.md`를 점검했다.
