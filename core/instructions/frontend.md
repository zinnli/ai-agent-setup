# 프론트엔드 규칙

React·TypeScript 기반 작업에 적용하는 규칙이다.

## 기존 코드 우선
- 기존 프로젝트의 패턴과 라이브러리를 우선한다.
- 새 의존성을 추가하기 전에 기존 구현으로 해결 가능한지 확인한다.
- 새 라이브러리가 필요하면 추가 이유와 대안을 먼저 제안한다.

## TypeScript
- `any`로 타입 오류를 우회하지 않는다. 불가피하면 `unknown` 후 좁히기를 쓴다.
- 타입 단언(`as`)보다 타입 가드를 우선한다.
- 공개 함수·컴포넌트의 props와 반환 타입을 명시한다.
- `@ts-ignore`, `eslint-disable`는 이유를 주석으로 남기고 최소 범위로 쓴다.

## React
- 컴포넌트는 단일 책임으로 작게 유지하고, 로직은 커스텀 훅으로 분리한다.
- 훅 규칙(최상위 호출, 조건부 호출 금지)을 지킨다.
- `useEffect`의 의존성 배열을 정확히 채우고, 부수효과가 아닌 로직은 넣지 않는다.
- 리스트 렌더링의 `key`에 배열 인덱스 대신 안정적인 식별자를 쓴다.

## 상태 관리
- 상태는 필요한 곳에 가장 가깝게 둔다. 불필요한 전역 상태를 만들지 않는다.
- 서버 데이터와 클라이언트 상태를 구분해 관리한다.
- 파생 가능한 값은 별도 상태로 두지 않고 계산한다.
- 기존 상태 관리 방식(Context, 스토어 등)을 따르고 새 방식을 임의로 도입하지 않는다.

## UI 상태
- UI 변경 시 로딩, 오류, 빈 상태를 함께 고려한다.
- 비동기 작업은 실패 케이스를 처리하고 사용자에게 피드백을 준다.
- 접근성(시맨틱 태그, 레이블, 키보드 조작)을 기본으로 고려한다.

## 테스트
- 동작을 바꾸면 관련 테스트를 함께 갱신한다.
- 구현 세부가 아닌 사용자 관점의 동작을 테스트한다.
- 새 기능·버그 수정에는 해당 케이스를 검증하는 테스트를 추가한다.
